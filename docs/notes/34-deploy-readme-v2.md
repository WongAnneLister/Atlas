# 34 — Public deployment, release process, and README v2

**What**
I added a multi-stage non-root `Dockerfile`, `docker-compose.prod.yml`, and a Caddy HTTPS config.
I added a UTC daily spend cap, a synthetic-data demo banner, and a full `.env.example`.
I wrote `docs/DEPLOY.md`, `docs/RELEASE.md`, `docs/RUNBOOK.md`, and an eval-gated release workflow.
I extended `make results` for Phase 2 metrics and upgraded `README.md` to v2.

**Why**
A public demo needs HTTPS, persistent storage, and a hard cap on daily LLM spend.
Without a spend cap and rate limits, one script can create an unbounded bill.
An eval-gated release workflow blocks bad deploys before they reach users.
Generating every README number from `eval/reports/` stops metrics from drifting out of date.

**Number**
No number yet.
This commit packages and documents earlier measured results rather than running a new eval.
All summary metrics in `README.md` are generated by `make results` from `eval/reports/`.

**Trade-off**
I chose one VM with Docker Compose and Caddy over a multi-service cloud PaaS.
That keeps fixed hosting costs low and avoids managing separate cloud vector databases.
The trade-off is single-region capacity without automatic horizontal scaling.
Also, no remote cloud VM was provisioned here, so live HTTPS smoke testing awaits deployment.

**Likely follow-up question**
Q: What happens when the public demo hits its daily LLM spend cap?
A: `DailySpendCap` checks daily UTC spend before acquiring a worker slot or calling any model.
Once the cap is reached, `/api/chat` returns a friendly `demo_budget_reached` handoff event.
The counter resets automatically at midnight UTC with zero manual intervention.
