## 0. What exists today (checked on 2026-11-22)

- Docs are generated by `support_agent.data.build_docs` (`make data-docs`). A section is
  `## <heading>` plus `<!-- section: <id> -->`; `validate_docs.SECTION` and `chunking.py` parse it.
  Ids are `<topic>.<dataset>.<slug>.<digest(category)>`, so the digest is the same across topics.
- The generic store's (MakTek) sections hold the date-relative rules worth versioning:
  `returns.md` line ~145 "return products within 30 days of purchase", and the generic-store
  section of `refunds.md` "If the price of a product drops within 7 days of your purchase".
- `Chunk` (`retrieval/chunking.py`) is dumped straight into Milvus rows (`MilvusStore.upsert`).
  `STORE_SCHEMA_VERSION = "1"` is part of the index fingerprint (`index_plan.py`), so a schema
  change forces a full build through the 22 lifecycle.
- The registry `sections` table already has a `metadata` JSON column (`index_tables.py`); it holds
  only `{"heading": ...}` today. No migration is needed for it.
- `Retriever.retrieve(query, top_k)` is the protocol (`retrieval/types.py`). `HybridRetriever`
  calls dense and BM25 separately; `RerankRetriever` wraps the hybrid one. `MilvusStore._search`
  passes no `filter`.
- Store scope (`retrieval/scope.py`) is a post-retrieval filter by store name. It stays.
- "Today" for the app is `settings.orders.today` (`2026-11-09`). The refund path already reads
  `order.order_date` from `OrderService` (`graph/nodes/refund.py::load_order`).
- Seeded orders are dated `today - randint(0, max_order_age_days=120)`, so 2026-07-12 to 2026-11-09.
  The spec's example change date (2026-06-01) has no orders before it.
- The refund policy query is built only from order facts (`graph/refund_query.py`) and names the
  generic store. `eval/refund_policy_eval.py` already runs `RefundPath.retrieve_policy` on every
  seeded order without an LLM.
- Eval sets are generated and gitignored (`eval/sets/*.jsonl`); `eval/registry.yaml` pins each
  file by sha256. `EvalItem` (`eval/schema.py`) has `extra="forbid"` and `Group` has five values.
- The 22 release check (`eval/index_release.py`) hashes `EvalItem.model_dump()` for its item set,
  and its `evidence_config_hash` covers retrieval, gate and Milvus settings.

## 1. Decisions and deviations from the spec

Each one goes in the final message and in the relevant doc.

1. **Synthesise past versions; keep today's text current.** The spec's example makes the new
   version differ from today's text. That would change the answers that eval_v1 gold labels
   expect. Instead, today's text stays the current version with its section id unchanged, and a
   synthetic *older* version gets a new id. eval_v1 stays valid without edits.
2. **Change date 2026-09-01**, inside the seeded order range. Every non-versioned section is valid
   from `policy_versions.default_effective_from: 2026-01-01`. Validity is half-open:
   `effective_from <= day < effective_to`. An order placed on the change date gets the new policy.
3. **Two versioned sections** (the spec allows 2–3):
   - generic-store returns: before 2026-09-01 "within 90 days of purchase"; from 2026-09-01 the
     existing "within 30 days". 90 days makes the date change the decision: an order placed on
     2026-08-20 is still inside 90 days on 2026-11-09, and outside 30.
   - generic-store refunds: before 2026-09-01 price drop "within 14 days"; current "within 7 days".
4. **Old version ids** are `<current id>@<effective_from>`, e.g. `returns.maktek_faqs.generic-store.<digest>@2026-01-01`.
   The heading gets the suffix ` (policy before 2026-09-01)` so a human reading a citation can tell.
5. **Dates in Milvus are INT32 `YYYYMMDD`.** An open end is `policy_versions.open_end_day: 99991231`
   in config, not a nullable field. The Python model keeps `date | None`. This avoids relying on
   nullable-field `IS NULL` support in Milvus 2.5.10. Verify the filter on the live server in 23b.
6. **A category filter keeps policy sections:** `doc_type == "policy" or product_category == "<c>"`.
   A plain `product_category == "<c>"` would drop the warranty and returns policy from a product question.
7. **The customer's text never sets the date.** The knowledge path filters by today. Only the
   refund path filters by a date, and only by the verified `order.order_date`. A customer who
   writes "I bought it in August" still gets today's policy on the knowledge path. The eval tests this.
8. **No "category boost" ablation.** A boost before the cross-encoder only changes which 50
   candidates reach the reranker; the reranker then reorders them. The ablation is: no filters /
   date filter / date + category filter. Record this deviation.
9. **Old-schema collections are searched without filters, recorded, not silent.** The first
   metadata build is released with the 22 paired check against the live build `f66917e9`, which
   has no metadata fields. A collection without the fields was built before versions existed, so it
   holds only current text. Retrieval records `filters_applied: false` in state and in eval rows.
   A collection with the fields always gets the filters. An empty filtered result is never retried
   without filters (spec requirement); the gate fails on empty retrieval and the path hands off.
10. **Answer notice is a code template, not model wording.** When a refund decision cites a chunk
    whose version is not current today, the reply starts with
    `graph/prompts/policy_version_notice.txt`, filled from order and chunk metadata.

## 3. Commit 23 — metadata and filtered retrieval

### 3.1 Metadata model (`retrieval/chunking.py`, `data/`)
- `Chunk` gains `doc_type` (`policy | catalog`), `topic`, `product_category` (`""` for policy),
  `effective_from: date`, `effective_to: date | None`, `region` (`"global"`).
- The docs builder writes `data/processed/docs/section_metadata.json` for every section; chunking
  reads it. A section without metadata is an error, not a default.
- Turn `policy_versions.enabled` on; rebuild the docs.
- The registry stores the metadata in `sections.metadata` next to the heading. A metadata change
  is a section change in `index_plan` (it is part of the content hash).

### 3.2 Milvus schema (`retrieval/milvus_store.py`)
- New scalar fields: `doc_type`, `topic`, `product_category`, `region` (VARCHAR) and
  `effective_from_day`, `effective_to_day` (INT32). Scalar indexes where Milvus 2.5 supports them
  (INVERTED on VARCHAR, STL_SORT on INT32). Byte limits from config.
- Bump `STORE_SCHEMA_VERSION` to `"2"`; the fingerprint then forces a full build. Read paths map
  the day ints back to dates. `supports_filters()` reports whether the collection has the fields.

### 3.3 Filters (`retrieval/filters.py`, new)
- `RetrievalFilters(as_of: date | None, product_category: str | None)`, a Pydantic model.
- `to_expr()` is a pure function: date → `effective_from_day <= D and effective_to_day > D`;
  category → `(doc_type == "policy" or product_category == "c")`; both → joined with `and`;
  none → `""`. Quote values safely; reject unknown categories.
- `matches(chunk)` implements the same rule in Python for the in-memory and fake retrievers.
  A test runs both on a grid of chunks and dates and requires the same result.
- `Retriever.retrieve(query, top_k, filters: RetrievalFilters | None = None)`. Hybrid passes the
  filter to **both** dense and BM25 before fusion; rerank passes it to its base; the store sends
  `filter=` to Milvus. Update every implementation and fake; existing callers keep working.

### 3.4 Category detection (`retrieval/categories.py`, new)
- A model number (reuse the gate's model-number extraction) maps to its category through the
  catalog `products.jsonl`. Category words come from config
  (`retrieval.filters.category_terms`). Exactly one category → filter; none or several → no category filter.

### 3.5 Paths (`graph/nodes/knowledge.py`, `graph/nodes/refund.py`)
- Knowledge: `RetrievalFilters(as_of=settings.orders.today, product_category=detected)`.
- Refund: `RetrievalFilters(as_of=order.order_date)`. No category. The date comes only from
  `OrderService`. Source blocks for the decision show each chunk's validity dates.
- Both record `filters` and `filters_applied` in state and in the handoff retrieval snapshot.
- Notice: if a cited chunk's version is not current today, the reply starts with the template,
  e.g. "Your order was placed on 2026-08-20. The policy that applied then was in effect from
  2026-01-01 to 2026-09-01." with that chunk's citation number.
- Config: `retrieval.filters: {enabled: true, category: true, category_terms: {...}}`. The ablation
  flags override these; they are part of `evidence_config_hash` and `score_config_hash`.

### 3.6 Eval wiring
- `production_chunks` (`eval/sweep.py`) applies the knowledge-path filters, so the 22 release check,
  the sweep and the evaluator measure what users see. Old-schema collections: §1.9.
- `eval/time_sensitive_eval.py` supports all three `--filters` modes.
- `eval/retrieval_eval.py`: add the three filter modes as ablation rows for v1 (dev and test).

### 3.7 Docs
- `docs/RETRIEVAL.md` (metadata, filters, ablation, §1 decisions), `docs/REFUND_FLOW.md` (order-date
  policy and notice), `docs/DOCS_BUILD.md`, `docs/ARCHITECTURE.md` if it lists retrieval steps.

### 3.8 Tests (offline; add, never weaken)
- Filter expression for each combination, quoting, unknown category, boundary days.
- `to_expr` and `matches` agree on the grid.
- Hybrid passes the same filter to both searches (fake store records it).
- Refund path uses the order date, never today and never a date in the customer's text
  (fake retriever records the filters).
- Knowledge path uses today plus the detected category; several categories → no category filter.
- Empty filtered result → handoff, zero answer-model calls, and no unfiltered retry.
- Old-schema collection → unfiltered, `filters_applied: false` recorded.
- Notice: appears for an old-version citation, absent for a current one; output guard keeps it.
- Graph tests assert the route (node sequence), as AGENTS.md §5.5 requires.
- Milvus integration test (`@pytest.mark.integration`): a scratch collection with two versions,
  dense and BM25 searches with a date filter each return only the version in force.
